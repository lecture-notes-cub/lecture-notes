Assessment Criteria For M3
M3 is worth 20 points, one fifth (1/5) of your total grade. You get one grade per team. Deadline: Mon 16.11.2026, 23:59. Late submissions receive at most 50% of the points (only commits pushed to main before the deadline are graded).

This is a comparison milestone. At M2 you built one agent and measured it. Now you build two new variants of it, run all of them on the same evaluation sample, and pick the one that is most rational for your task.

If you would like to change your set/M2 version of your agent, do that first. Anyways, in the end, you need to have 3 variants of your agent.

What counts as a variant?
Focus on the key idea of this milestone: we grade the logic of what you decided to change and why, not how close you got to perfect eval numbers (although good numbers are great).

By now you can think about agents at a higher level of abstraction than before the course, in terms of decision-making, reasoning patterns, tools, context and memory, and M3 is where you show it. You should submit 3 variants, counting M2 as a variant, on the same evaluation set. If you would like to fix your M2 agent - then fix it first and submit as a new variant).

Do not change things in the code at random. Look at your M2 traces, form a hypothesis such as "our agent needs better context engineering", "our tools are the bottleneck" or "the model should make this decision instead of the code", and build each new version of your agent from that hypothesis, so that every change follows from your understanding of what you are doing with the agent and why. That's the whole point.

Each variant should come from one of the patterns you have seen in the lectures.

You can change the decision-making, that is, which decisions the model makes and which the code makes: move a step from code to the model or back, add a stop rule, or let the model decide when to ask the user (L5).

You can change the reasoning pattern, that is, how the model gets from the task to the next action: ReAct against plan-and-execute, or a self-check before the final answer (L2–L3).

You can change the tools, that is, what the model can call and how it is described: one coarse tool against several fine-grained ones, rewritten tool descriptions and schemas, or hiding tools that are not relevant (L4–L5).

You can change the context, that is, what is in the window at each call: clearing old tool results, compaction, recitation of a todo file, or a subagent that returns a summary (L6–L7).

You can change the memory, that is, what persists across steps or runs: no memory, a scratchpad file, or episodic memory of past runs, RAG.

Finally, you can replace your own loop with a ready-made harness and port the same agent and tools to one SDK, such as the Claude Agent SDK, the OpenAI Agents SDK, LangGraph, Google ADK or smth else.

Changing just the model is allowed for at most one of the three variants but has to be done with a proper hypothesis & explanation (I suggest being mindful about that, if you have a reasonable model choice already - it would be hard to argue a different model choice).

Testing cheaper or smaller models, or smaller models with some changes in the harness in order to reach the same performance but cheaper, is a fantastic strategy to pursue for your M3 assignment, though. I hope you get the idea.

Some changes do not count as variants. Rewording the prompt or changing the temperature and other sampling settings is not a variant. Bug fixes are not variants either: if your M2 agent crashed, fix it in your M2 agent and re-run M2 before you compare. You can change more then one thing (e.g. porting to SDK + model change) per variant.

Infrastructure work that every agent needs anyway, such as running it in Docker or a sandbox, adding security checks, tracing or logging, is expected regardless to achieve the M3 results and, therefore, is not a variant.

What will be graded?
Two new variants with hypotheses (existing M2+2 or fixed/new M2+2) (5 pt).

You built three new variants of your M2 agent, each changing a different mechanism. Two variants may come from the same pattern only if they test genuinely different mechanisms within it. For each variant, write down before you run the evaluation which mechanism it changes, what you expect to improve, on which tasks and through which decision in the trace, and where the idea comes from. Commit the hypotheses before the evaluation results, so that git history shows the order.

Comparative evaluation on the same sample (10 pt).

You ran your M2 agent and all three variants on the same frozen M2 sample with the same evaluation method you used at M2. Report the results side by side in one place: for every variant, including the baseline, give the success rate together with steps and calls per task, tokens per task, $ per task and latency per task (what applies in your case). Success without cost is not a result.

If you use an LLM-as-judge (we will discuss it on 5.11), it must be the same judge with the same rubric as at M2, and you report how often it agrees with your own labels.

Rational selection (5 pt).

You pick a winner and argue the choice in terms of rationality. A rational agent maximises the expected value of its performance measure, given what it perceives and what it knows. Rationality is therefore a property of the pair of the agent and its performance measure, not of the agent alone.

Start from your performance measure: restate it from your M1 PEAS description, and show that the winner is the variant that best serves it. This is not necessarily the variant with the highest success rate. You should argue which variant you consider the winning one. How different is it from the other ones? Do the agents differ from each other by more than a single agent differs from itself across runs?

Deliverable
The code in your repo contains all variants, runnable from one entry point with a variant flag, the eval script and the same frozen sample as in M2.

The documentation (M3.md or a section of the README) describes each variant with its mechanism, hypothesis and source, gives the comparison of all variants with costs, the per-task breakdown, the baseline comparison, pass^k for the winner and the selection argument.

The traces from all evaluation runs are committed to the repo, with the variant name in every record.

Reproducibility follows the same rules as in M2. For cloud and API models, provide .env.example (no real keys in the repo!!!), the exact commands to run each variant and the eval, and the expected output. For local models, record a short screen video (3–5 min) that shows at least two variants on the same task with the traces being written, and document the model name, size and quantization.

You can use any third-party code and architectural ideas from papers and systems: cite them in comments and check the licenses.

Please submit the repo link. A submission from one team member is enough.

What's happening next
After M3 your team will be assigned one other team's repo to review.

You do not need to write any code for the peer review. You prepare a structured report with meaningful feedback for your colleagues, using at least two different coding agents/language models (for example, proprietary ones) to help you reviewing other team's agents. You would need to organize a meeting with them to exchange ideas.

Peer review is worth 1/5 of your total grade like any other milestone.

In turn, you will receive a review of your own repo.

For M4 and your final presentation, you read that feedback critically, decide whether it was helpful, argue with your colleagues where you disagree, and prepare the final report and presentation on 17 December, explaining which changes you made in response and why.

# Team M3 pre-registration (written before M3 evaluation)

## Performance measure

The agent should produce useful, structurally valid study notes whose key claims,
numbers and formulas are grounded in the assigned lecture interval. Subject to that
quality requirement, fewer model calls, tokens and seconds are better. A run that
finishes is not automatically successful. We report the M2 lexical proxy for
continuity, but prioritize the small team-reviewed key-claim score because the M2
feedback showed that copying the transcript can score 97.5% lexical coverage.

The frozen transcript, task wording and intervals remain those from M2. The additive
`eval/key_claims.json` labels are evaluation-only and are never supplied to an agent.
Its current annotation status is pending team verification; it must be reviewed and
marked verified before the measured M3 run.

## Pre-registered variants and hypotheses

### `m2_loop` — M2 ReAct-style control

Mechanism: the model repeatedly chooses among interval reads, literal search, draft
saves and finish. The complete visible action/observation history is retained.

Hypothesis: this should remain the most flexible variant, but M2 traces suggest that
flexibility is often wasted. It is expected to use more calls than `lean_loop`
without reliably improving key-claim accuracy. Searches that return no matches and
repeated save/repair decisions are the expected trace-level failure signals.

Source: the M2 implementation and the ReAct/tool-use patterns from L2–L5.

### `lean_loop` — bounded plan-and-execute

Mechanism change: code hides `search_transcript`, permits exactly one read of the
whole assigned interval, permits at most two saves, and caps execution at four
decisions: read, draft, optional revision, finish. This is enforced by both the tool
schema and runtime rather than being only a prompt change.

Hypothesis: on the current short, pre-selected intervals, one complete read contains
enough evidence. `lean_loop` should retain comparable structure and key-claim scores
while reducing calls, tokens and latency. It may lose on long/noisy tasks such as t08
and t16, where selective rereading could help. A successful trace should contain one
source read, no searches, one or two saves, and finish within four decisions.

Source: plan-and-execute, tool hiding and code-controlled stop rules from L2–L5.

### `claim_check` — enforced self-check before finish

Mechanism change: the model receives a `check_claims` tool that returns the current
draft, extracted draft numbers and assigned source evidence. Code rejects `finish`
unless the latest saved draft has been checked; every revision invalidates the check.

Hypothesis: the extra review should improve grounded key claims, especially the
misplaced citations/unsupported connection in t01/t03 and the numerical errors found
in t17/t19. It should cost at least one extra model call and increase latency. The
expected causal trace is save → check_claims → either finish or revise → re-check →
finish. Finishing without that transition is impossible by construction.

Source: self-reflection/self-check reasoning from L2–L3 and a code-controlled finish
gate from L5.

### `one_call_baseline` — non-agent comparison

One model call receives the complete assigned source and directly writes notes. It
is not counted among the three agent variants, but is evaluated with the same labels,
model and decoding settings.

## Evaluation protocol fixed before results

- Run all four configurations on the unchanged 20-task M2 sample with Qwen3 4B.
- Report per task and aggregate finish, structure, lexical coverage, key-claim score,
  model/tool calls, input/output tokens, latency and local API cost ($0).
- Keep the optional M2 local-model judge unchanged when used; it remains a proxy.
- Repeat the selected winner to report pass^k and compare between-run variation with
  between-variant differences.
- Preserve every notes file, stats file and JSONL trace. Every trace record includes
  its variant name.

The primary comparison is key-claim quality subject to cost. Lexical coverage is a
secondary continuity metric, not factual ground truth. Results, per-task breakdown,
pass^k and winner selection will be added only after labels are team-verified and the
evaluation is run.
